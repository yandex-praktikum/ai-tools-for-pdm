# Карточка кейса — «Кто выгуливает Бориса»

## Задача

По `spec.md` собрать учебный micro-MVP для вымышленной компании «Догяндекс»: общая страница, на которой сотрудник записывается на прогулку с офисным псом Борисом в один из пяти фиксированных слотов дня (09:00–17:00), видит занятые и свободные слоты, а повторная запись в занятый слот отклоняется сервером. Дополнительная функция — карточка «Последнее кормление». Состояние — в SQLite, главный сценарий должен работать на широком и узком экране.

## Что сделано

**Архитектура** (минимальная, без внешних зависимостей):

- `server.js` — HTTP-сервер на встроенном модуле Node.js: статика из `public/`, API слотов и кормления
- `db.js` — SQLite на встроенном `node:sqlite`: схема из `spec.md` дословно (включая CHECK-ограничение), автосоздание пяти слотов на текущую дату (`INSERT OR IGNORE` + `UNIQUE`)
- `public/` — страница, стили с адаптивом, клиентская логика; ФИО выводится через `textContent` (без innerHTML)

**Ключевое техническое решение** — защита от двойной записи одним атомарным оператором:

```sql
UPDATE walk_slots SET booked_by = ?, booked_at = ?
WHERE walk_date = ? AND slot_time = ? AND booked_by IS NULL
```

Если строка не изменилась — слот успели занять, сервер отвечает 409 с понятным сообщением, первоначальная запись не трогается. Никакого «прочитать, проверить, записать» — гонки исключены на уровне SQLite.

**Процесс работы с ИИ-агентом** — по правилам `AGENTS.md`: одна задача за итерацию → агент называет затрагиваемые файлы и способ проверки → правка → фактическая проверка → фиксация наблюдаемого факта в `PLAN.md`. Так пройдены шесть шагов: каркас → база → страница слотов → запись с атомарной защитой → кормление → адаптив и финальный smoke-check.

## Результат

Все семь DoD из `spec.md` выполнены и подтверждены наблюдаемыми фактами (фиксация в `PLAN.md`, скриншоты `screenshots/1–7.png`, демо-видео в комментарии PR):

1. Дата и ровно пять слотов на странице
2. Свободные и занятые различаются, у занятого видно ФИО
3. Запись в свободный слот с синтетическим ФИО, состояние обновляется
4. Повторная запись — отказ 409 от сервера, исходная запись не меняется (проверено и 10 одновременными запросами: ровно один успех)
5. Данные в SQLite: сохраняются после F5, видны во втором браузере, переживают перезапуск сервера
6. Карточка кормления показывает время и ФИО, обновляется после отметки
7. На 360px нет горизонтальной прокрутки, сценарий читаем

## Вывод

Главный урок — не про код, а про процесс. Спецификация оказалась полноценным инструментом управления: когда требования записаны как наблюдаемые проверки (DoD), «готово» перестаёт быть вопросом мнения — либо факт зафиксирован, либо нет. Второй урок — доверять состояние базе, а не браузеру: кнопка в интерфейсе может что угодно показывать, и единственная честная защита от гонки — атомарная операция на сервере. Третий — работа с ИИ-агентом по одной задаче за итерацию с обязательной проверкой результата: агент ускоряет написание кода, но ответственность за «работает ли это на самом деле» остаётся на мне.
