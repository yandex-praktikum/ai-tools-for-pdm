# След одной итерации с ИИ — Шаг 4: запись в слот

Пример полного цикла «задача → агент → проверка → принятие» по правилам `AGENTS.md`. Взят Шаг 4 из `PLAN.md` — запись на прогулку с атомарной защитой от конфликта: это самое рискованное место проекта (гонки, потеря данных), поэтому его и показываю.

## 1. Какую задачу я поставил агенту

После принятия Шага 3 (страница со слотами) я дал задачу: **«Шаг 4 — запись в слот»** по плану:

- ввод ФИО и подтверждение в свободном слоте;
- запись в SQLite, состояние после действия обновляется;
- повторная запись в занятый слот отклоняется **сервером** — не скрытием кнопки;
- проверка — DoD 3–5 из `spec.md`.

## 2. Что сделал агент

По правилам перед правками агент назвал план: затрагиваемые файлы (`db.js`, `server.js`, `public/app.js`, `public/style.css`), ожидаемый эффект, способ проверки. Затем:

- **`db.js`** — функция `bookSlot()`: один атомарный `UPDATE … WHERE booked_by IS NULL`. Результат операции (`changes`) — источник истины: ноль изменённых строк значит «слот уже заняли»;
- **`server.js`** — маршрут `POST /api/book`: валидация ФИО (непустое после `trim`) → 400; несуществующий слот → 404; занят → 409 с текстом «Этот слот уже занят. Выберите другой.»; успех → 200;
- **`public/app.js`** — форма только у свободных слотов; после любой попытки список слотов перезагружается с сервера (сервер — источник истины, а не локальное состояние страницы); при конфликте показывается сообщение.

Важный момент: агент **не** сделал «прочитать слот, проверить, записать» — ровно то, что `spec.md` прямо запрещает из-за гонки между двумя сотрудниками.

## 3. Как я проверил результат

Агент прогнал свои проверки и честно показал вывод, а я проверял независимо:

**В браузере :**

1. заполнил форму свободного 09:00, отправил — слот стал «Занят — Мария Тестова», форма исчезла, без перезагрузки страницы;
2. обновил страницу (F5) — запись на месте (DoD 5: SQLite, а не память страницы);
3. открыл вторую вкладку — состояние то же.

## 4. Почему принял

Три причины:

1. **Факты, а не обещания.** Каждая ветка (200/400/404/409) подтверждена реальным ответом сервера, а ключевой сценарий — моими глазами в браузере, включая F5 и вторую вкладку. Проверка «повторная запись не перезаписывает чужое ФИО» — ровно требование DoD 4.
2. **Правильное место защиты.** Отказ приходит от сервера из одной атомарной операции, а не из логики интерфейса — как требует `spec.md`. Значит, защита работает и для любого другого клиента (curl, второй браузер), не только для моей страницы.
3. **Скоуп не расползся.** Агент не притащил лишнего: ни авторизации, ни отмены записи, ни фреймворков — ровно задача Шага 4.

После принятия я зафиксировал факт в `PLAN.md`: отметил Шаг 4 выполненным с фактической проверкой и датой, и мы перешли к Шагу 5.

## Что пошло не так по ходу (и это тоже часть итерации)

Две нештатные ситуации, которые агент нашёл и решил сам, а я проверил: осиротевший процесс `node`, державший порт 3000 после остановки обёртки `npm` (из-за него новый сервер падал с `EADDRINUSE`), и curl из Git Bash, отправлявший кириллицу в битой кодировке (дефект тестового инструмента, не сервера — из браузера UTF-8 приходил корректным). Урок: доверяй проверкам, но всегда спрашивай себя, что именно проверяет инструмент.
